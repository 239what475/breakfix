# Shell、文件与配置定位

**Topic ID：**`shell-files-and-configuration`
**Domain：**Linux 系统与网络运维
**状态：**首轮核心场景设计，尚未实现为运行时题目

## 范围

本 Topic 训练学习者从进程参数、服务日志、文件类型和符号链接中确认“实际被使用的对象”。重点不是记忆 `grep`、`find` 或 shell 参数，而是在看似正确的文件与真实运行状态不一致时建立证据链。

## 建议前置知识

基本 shell 导航、绝对路径与相对路径、文件所有权，以及阅读简单配置文件的能力。

## 学习导读

### 学习目标

- 区分“文档中存在的配置”和进程实际加载的配置。
- 从进程参数、journal、文件类型和链接解析建立配置生效链路。
- 以规范路径修复发布或配置漂移，而不是留下临时副本。

### 核心心智模型

服务不会因为一个文件看起来正确就采用它。命令行参数、环境文件、符号链接和配置优先级共同决定进程的有效输入；文件名存在也不代表链接目标或目录结构有效。

### 诊断证据与工具

先比较进程实际参数、服务 journal 和对外响应，再检查配置树、文件类型和链接目标。`readlink`、`stat`、`systemctl` 与文本检索各自用于建立不同证据，不能只依赖其中一个。

### 常见误区

- 只修改第一个找到的配置文件，而不确认它是否被加载。
- 将失效链接替换为临时普通文件，破坏发布布局。
- 用手工启动或额外服务绕过受管配置问题。

### 面试追问

- 如何证明某个配置文件是进程当前真正使用的输入？
- 配置文件存在、权限正确但服务仍失败时，下一步会检查什么？

### 推荐关系

建议先学习本 Topic，再进入 systemd、日志和网络服务 Topic；权限 Topic 可与本 Topic 并行学习。

## 核心场景

### `trace-orders-api-effective-config`：定位实际生效的配置

- **环境地图：**`client -> gateway -> app`；app 运行 `orders-api.service`，gateway 反向代理到 app。
- **本题相关知识：**生效配置、进程参数、环境文件、配置优先级。
- **学习目标：**从运行证据定位配置覆盖来源，并恢复唯一的受支持配置输入。
- **初始状态：**`app` 上的 `orders-api.service` 正常启动，但 unit 的启动参数引用了一个遗留环境文件；`/etc/orders-api/runtime.env` 内容正确，遗留文件把服务监听地址设为错误值。journal 会记录实际加载的文件路径。
- **用户看到的症状：**服务进程存在，但从 `gateway` 访问 API 失败；直接阅读文档中的主配置又看不出问题。
- **任务边界：**恢复受支持配置路径的唯一性；不能通过在 gateway 中绕过 API、修改应用代码或额外启动一个副本掩盖故障。
- **完成条件：**`orders-api` 从规定的 `/etc/orders-api/` 配置树读取运行参数，并以文档定义的地址和端口提供响应。
- **检查点：**服务为 active 且监听文档定义的地址/端口；`gateway` 能连通 API；client 经服务名称获得预期响应。
- **提示层级：**方向：比较“文件内容正确”与“服务实际行为”的差异；证据：查看进程参数和 journal 对配置来源的记录；概念：配置优先级由启动输入决定，而非文件名或文档决定。
- **解答与复盘：**将客户端失败限定到 app 的实际运行参数，追踪遗留环境文件如何覆盖规范配置，恢复单一权威来源后从整条 HTTP 链路验证。生产中应记录配置来源和发布 revision，避免同名配置静默漂移。
- **作者 verifier：**服务 reload/restart 后仍使用规范配置；遗留文件不再重新覆盖；未通过修改 gateway 或启动额外 API 副本达成通过。
- **能力状态：**可在“内部 Web 服务链路”实现。

### `repair-orders-config-symlink`：修复失效的配置符号链接

- **环境地图：**`app` 运行 `orders-api.service`；运行配置位于 `/etc/orders-api/`，发布版本位于 `/srv/orders-api/releases/`。
- **本题相关知识：**符号链接、文件类型、规范路径、发布版本。
- **学习目标：**识别链接存在与链接可解析的区别，并在保留发布布局的前提下恢复服务。
- **初始状态：**`/etc/orders-api/runtime.env` 是指向当前发布配置的符号链接。一次不完整发布删除了它的目标目录，前一份完整发布仍保存在 `/srv/orders-api/releases/`。
- **用户看到的症状：**`orders-api.service` 启动失败，journal 报告无法打开运行配置；同目录中的链接名称看起来仍然存在。
- **任务边界：**恢复既有发布布局和规范路径；不能把配置复制到临时目录、把链接改成随意的普通文件，或删除可用于诊断的发布记录。
- **完成条件：**规范链接解析到完整且可读的发布配置，服务能够启动并返回预期健康响应。
- **检查点：**规范路径可解析到可读运行配置；服务成功启动；API 健康端点返回预期响应。
- **提示层级：**方向：不要把链接名称存在当作配置可用；证据：检查链接目标、文件类型和发布目录完整性；概念：符号链接保存的是路径引用，目标被删除后链接本身仍会显示存在。
- **解答与复盘：**由 journal 的打开失败回溯到规范路径，解析链接并比较可用发布版本，恢复指向完整版本的引用。生产发布应在删除旧版本前验证所有活动链接的目标。
- **作者 verifier：**服务重启后仍读取规范链接；链接保持为链接而非临时普通文件；无关发布记录未被删除。
- **能力状态：**可在“单机运维主机”实现。

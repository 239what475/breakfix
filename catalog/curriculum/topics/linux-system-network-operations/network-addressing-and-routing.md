# 网络地址与路由

**Topic ID：**`network-addressing-and-routing`
**Domain：**Linux 系统与网络运维
**状态：**首轮核心场景设计；依赖 `CAP_NET_ADMIN` 与隔离网络 capability probe

## 范围

本 Topic 关注私网地址、路由选择、下一跳和地址冲突的证据链。它不假定学习环境等同裸机网络，也不允许题目修改宿主机、集群网络或其他用户的拓扑。

## 建议前置知识

Shell、文件与配置定位；DNS 与名称解析；端口、TCP 与 HTTP 服务。

## 学习导读

### 学习目标

- 按名称解析、地址、路由、邻居和服务监听分层定位私网连通性问题。
- 解释前缀、下一跳和地址所有权如何影响端到端请求。
- 在隔离拓扑内做最窄的网络状态修复，不破坏无关路径。

### 核心心智模型

DNS 成功只证明名称到地址，不能证明数据包能到达服务。路由决定发送给谁，邻居解析决定二层目标，重复 IP 会让这些观察在时间上不稳定；必须按层而不是按猜测排查。

### 诊断证据与工具

使用路由表、地址列表、邻居状态以及逐段 HTTP/TCP 连通性。每一次观察都应回答“问题在名称、路径、地址归属还是服务端”，不能从 timeout 直接推断唯一根因。

### 常见误区

- 因为 DNS 返回正确地址就跳过路由检查。
- 用 hosts、隧道或改服务端口绕过错误路径。
- 给节点添加任意地址或静态 MAC 绑定以掩盖 IP 冲突。

### 面试追问

- `Connection refused` 与 timeout 在路径定位上分别意味着什么？
- 如何证明间歇性访问是重复地址而不是 DNS 缓存或应用抖动？

### 推荐关系

建议在 DNS 和端口/TCP 基础后学习。所有核心场景必须等待隔离路由实验网络的 capability probe。

## 核心场景

### `repair-service-subnet-route`：修复服务子网路由

- **环境地图：**路由实验网络包含 `client`、`gateway` 和 `app`；app 位于 `10.42.20.0/24`，gateway 是题目规定的转发节点。
- **本题相关知识：**CIDR 前缀、下一跳、路由表、分段连通性。
- **学习目标：**在 DNS 和服务监听均正常时，将连接 timeout 精确归因到服务子网的错误路由。
- **初始状态：**`client` 访问 `app` 所在的 `10.42.20.0/24` 时使用了退役下一跳；DNS 和 app 的监听状态均正确，`gateway` 是该子网的规定转发节点。
- **用户看到的症状：**名称能解析为预期私网地址，`client` 到 app 的连接超时，而 `gateway` 到 app 的请求成功。
- **任务边界：**只修复 `client` 到服务子网的路由；不能改 DNS、修改 app 地址、破坏默认路由或通过 gateway 建立不受管隧道绕过问题。
- **完成条件：**client 经规定下一跳稳定访问 app，其他已有私网连通性保持不变。
- **检查点：**服务子网存在可用的正确路由；client 能请求 app 的健康端点；client 经 gateway 的端到端请求成功。
- **提示层级：**方向：在名称已正确的前提下，逐段比较 client、gateway 与 app 的可达性；证据：检查服务前缀的路由和下一跳；概念：最长前缀匹配决定某个目标网段使用的转发规则。
- **解答与复盘：**先排除 DNS 与 app listener，再由 gateway 成功、client 超时的差异锁定 client 路由，恢复服务子网的正确下一跳。生产网络应将预期前缀和下一跳作为可审计配置，而非依赖临时静态路由。
- **作者 verifier：**默认路由和无关子网不变；不通过隧道、hosts 或改 app 地址绕过；路由在题目规定的持久化机制下保留。
- **能力状态：**仅在“路由实验网络” probe 通过后实现。

### `diagnose-private-ip-conflict`：诊断私网 IP 冲突

- **环境地图：**`app` 的规定地址为 `10.42.20.10`；同一私网还有一台废弃训练节点，它应使用题目提供的替代地址。
- **本题相关知识：**IP 地址所有权、邻居解析、ARP/NDP、间歇性连通性。
- **学习目标：**将时好时坏的请求与不稳定邻居解析关联，恢复单一且明确的地址归属。
- **初始状态：**`app` 的规定地址为 `10.42.20.10`。一台废弃的训练节点错误保留了同一地址，导致 `client` 的邻居解析在两个节点间切换；该节点应使用题目提供的替代地址。
- **用户看到的症状：**同一 API 请求时好时坏，DNS 始终返回正确地址，邻居表和连接日志显示目标 MAC 不稳定。
- **任务边界：**恢复唯一的地址归属；不能修改服务名称、禁用邻居发现、静态绑定错误 MAC，或给 app 随意换未声明的地址。
- **完成条件：**`10.42.20.10` 只属于 app，client 对 API 的访问稳定，废弃节点使用其指定的替代地址。
- **检查点：**规定地址只有一个可观察所有者；连续 API 请求稳定成功；废弃节点可通过规定替代地址访问。
- **提示层级：**方向：将“地址正确”与“地址唯一”分开确认；证据：比较节点地址、邻居状态和连续请求结果；概念：同一二层网络上重复 IP 会使目标 MAC 在时间上翻转。
- **解答与复盘：**根据不稳定 MAC 和 DNS 一致性排除名称问题，识别两个地址所有者后恢复规定拓扑。生产环境应把 IPAM、冲突检测和变更审计结合起来，避免依赖人工记忆地址分配。
- **作者 verifier：**未使用静态错误 MAC 或关闭邻居发现；无关节点地址不变；重启网络服务后冲突不再出现。
- **能力状态：**仅在“路由实验网络” probe 通过后实现。

# Linux Domain 内容模型

**状态：**课程内容契约，不是运行时 schema。

本文件规定 Linux Domain 的教学信息如何进入 Topic 导读和场景卡。目录和筛选仍以 `Domain -> Topic -> Challenge` 为准；“考点”只是读者可理解的学习目标文本，不是新的目录层级或稳定关系键。

## 读者看到的三层内容

### 1. Topic 学习导读

每个 Topic 必须说明：

- **学习目标：**掌握后能独立判断的运维现象与边界。
- **核心心智模型：**系统中哪些对象相互影响，避免把命令记忆当作理解。
- **诊断证据与工具：**日志、状态、配置、网络观察各能证明什么；不列无上下文的命令清单。
- **常见误区：**看似有效但不安全、不可持续或会扩大影响面的处理方式。
- **面试追问：**帮助把场景中的证据和取舍解释给他人，不作为自动评分内容。
- **推荐关系：**建议先理解哪些 Topic；它只服务学习导览，不能锁定挑战。

### 2. Challenge Problem

每道题在用户开始排障前提供：

- **业务背景与环境地图：**说明服务价值、可进入的节点和已知服务关系，不泄露根因或平台实现。
- **本题相关知识：**两到四个自然语言考点，例如“目录的 search 权限”或“名称服务顺序”。它们描述应掌握的概念，不能直接写成“修复失效的某文件”。
- **学习目标：**题目结束后应能建立何种证据、区分哪些相似症状、遵守哪些运维边界。
- **症状、任务边界、完成条件和公开 checkpoint：**只描述学习者当前能观察或达成的状态。

学习材料不能预先给出确切根因、完整命令、唯一配置文件位置或唯一编辑方式。诊断题的价值在于学习者根据证据缩小故障域，而不是按讲义逐句照做。

### 3. Hints、Solution 与复盘

每个 checkpoint 未来都有对应 hint，按固定层级递进：

1. **方向：**指出应从进程、日志、解析、权限或网络路径中的哪一类证据开始。
2. **证据：**说明应比较哪些可观察事实，不直接给出完整命令或答案文件。
3. **概念：**解释所需机制，例如 systemd drop-in 优先级、ACL mask 或 TLS 信任链。

`solution.md` 不只是参考命令，必须以“诊断 -> 根因 -> 修复原则 -> 验证 -> 预防/监控”说明。它可按 checkpoint 标记组织解释，但 checkpoint 没有完成顺序，解答也不能暗示学习者必须按固定步骤操作。

## 公开 checkpoint 与作者 verifier

公开 checkpoint 只观察当前、用户有意义的结果，例如 API 响应、私网名称解析、批准身份可访问资源或服务持续输出日志。

以下内容属于作者 verifier，不出现在学习者的周期检查点中：

- 重启、reload、升级或重新生成后的持久性。
- 无关服务、路由、hosts 条目、软件包 hold 或配置对象未被修改。
- 负向安全边界的详细穷举。
- 规定实现文件、固定链接目标、unit drop-in 是否被删除等实现偏好。

verifier 仍应验证这些条件，只是不能把它们伪装成学习者在页面上等待通过的业务 checkpoint。

## 作者覆盖矩阵

每个核心场景必须在 Domain 的 `coverage.md` 中登记：主 Topic、实验系统、环境拓扑、相关知识、主要证据、根因类别、能力状态和与既有题的差异。新增场景只有覆盖新的故障模型、证据类型、约束或合理跨 Topic 组合时才进入候选制作。

这份矩阵用于内容审查和去重，不属于 portable candidate，也不应被同步到用户环境。
